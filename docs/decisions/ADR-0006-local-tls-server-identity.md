# ADR-0006: Local TLS Server Identity

## Status

Accepted.

## Context

Device credentials must not be sent as reusable bearer secrets over unrestricted cleartext HTTP. The backend runs on private LAN addresses that may change, and public CA certificates are not practical for arbitrary local laptop IPs.

## Decision

localSync uses a persistent self-signed local TLS identity generated by the backend under the configured runtime data root.

The initial implementation generates an ECDSA P-256 private key and self-signed X.509 certificate with stable logical hostname `localsync.local`. The canonical server identity fingerprint is the SHA-256 digest of the certificate SubjectPublicKeyInfo, encoded as base64url and prefixed with `spki-sha256:`.

Network address is a locator, not identity. Future discovery can update the current address for the same trusted server identity.

## Consequences

- The backend can reuse the same identity across restarts.
- Android and fake clients can compare/pin a stable public-key fingerprint.
- Certificate renewal can keep the same public key if needed without changing the canonical identity.
- Clients must not use trust-all TLS. Any special first-pair trust handling must be scoped only to observing/displaying the first fingerprint.
- Android normal traffic uses `localsync.local` as the request hostname, scoped DNS maps that logical host to the current LAN locator, and normal hostname verification remains enabled.

## Alternatives Considered

- Trusting private IP address certificates: rejected because DHCP changes addresses.
- Public CA certificates: rejected for arbitrary local-only laptop addresses.
- Trust-all certificate managers: rejected because they destroy the security property.
- Certificate fingerprint instead of SPKI fingerprint: simpler, but less flexible for certificate renewal.
